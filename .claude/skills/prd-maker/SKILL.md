# PRD 작성기

기능 아이디어·요구사항 메모를 이 프로젝트(InfluencerSeeder, **PyQt6 + Selenium + CSV** 데스크탑 앱)
컨벤션에 맞는 **구조화된 PRD**로 작성한다. 결과물은 `.claude/tasks/prd-*.md` 로 저장하고,
이후 `task-maker` 스킬이 이 PRD를 읽어 작업 목록을 생성한다.

> **연계:** `prd-maker`(이 스킬) → `task-maker`(PRD→tasks) → `task-runner`(실행) → `task-cleaner`(정리)

---

## 입력 처리

1. **인자가 파일 경로면** → 그 메모/초안을 읽어 구체화 (기존 `prd-260610-3.md`처럼 거친 메모를 PRD로 승격).
2. **인자가 기능 설명이면** → 그 설명을 토대로 작성.
3. **인자가 없으면** → `.claude/tasks/` 에서 가장 최근 `prd-*.md`(구조화 안 된 메모)를 찾아 구체화 제안.

기존 PRD가 있으면(`prd-260610-2.md` 등) **반드시 먼저 Read** 하여 버전 연속성을 유지하고,
새 PRD는 "이전 대비 증분(delta)"을 명확히 한다.

---

## 작성 전 인터뷰 (모호한 부분만 질문)

메모/설명에서 아래가 불명확하면 `AskUserQuestion`으로 **꼭 필요한 것만** 묻는다.
이미 메모에 답이 있으면 묻지 말고 진행한다.

- 이 기능의 **사용자 시나리오**(누가, 언제, 무엇을 위해)
- v1/v2 대비 **무엇이 바뀌는가**(신규 / 변경 / 제거)
- **데이터 스키마** 변화 (CSV 컬럼, 설정 키)
- **UI 변화** (어느 패널/탭/다이얼로그)
- **범위 밖(Non-Goal)** 으로 둘 것

`.claude/tasks/` 의 스크린샷(`*.png`)이 관련되면 **Read로 직접 열어** 화면을 파악한 뒤 반영한다.

---

## 프로젝트 컨텍스트 (PRD에 반영할 기준)

작성 전 아래를 참조해 현실과 맞는 PRD를 쓴다:

| 참조 | 경로 | 용도 |
|------|------|------|
| 아키텍처/패턴 | `src/CLAUDE.md` | 신호/슬롯, 디자인 토큰, 스토리지, 테스트 격리 규칙 |
| 기존 PRD | `.claude/tasks/prd-260610-2.md`, `prd-260610-3.md` | 버전 연속성, 포맷 |
| 코드 구조 | `src/core/`, `src/ui/`, `src/design/`, `src/tests/` | 실제 모듈명·시그니처 |
| 스크린샷 | `.claude/tasks/*.png` | UI/플로우 |

**핵심 제약 (PRD가 위반하면 안 됨):**
- 저장은 **CSV/JSON 파일 기반** (구글시트·서버 없음 — v2에서 제거됨).
- 인스타 **크리덴셜 저장 안 함** (사용자가 직접 로그인).
- UI는 `QThread` 신호로만 갱신 (스레드에서 위젯 직접 조작 금지).
- 색상은 `design/tokens.py` 참조 (QSS에 hex 직접 금지).

## PRD 표준 구조 (이 프로젝트 포맷)

`prd-260610-2.md` / `prd-260610-3.md` 의 검증된 포맷을 따른다:

```markdown
# PRD: InfluencerSeeder v[N] — [한 줄 제목]

> [이전 PRD 대비 이 문서의 위치/증분을 1~2줄로]

## 1. 배경 & 문제 정의
- (메모 기반이면) 원본 요구사항 → 해결할 문제 매핑 표

## 2. 범위 (Scope) / Non-Goals
- 포함 / 제외 명시

## 3. 핵심 시나리오
- 사용자 흐름 (수집 시작 → 로그인 → step 순회 → 저장 → 재개)

## 4. 기능 요구사항 (FR)
- FR-01 … 검증 가능한 단위로

## 5. 데이터 스키마
- `data/*.csv` 컬럼·키 + 기본값 (실제 코드형식으로)

## 6. UI 변경
- 어느 패널/탭/다이얼로그(QStackedWidget/QTabWidget) — 위젯 단위로

## 7. 코드 변경 요약 (구현 가이드)
- `core/`, `ui/`, `design/` 모듈별 함수 시그니처 수준으로

## 8. 테스트 계획
- `tests/test_*.py` — pytest, 외부 의존성 mock 격리

## 9. Non-Goals
## 부록 A — 원본 요구사항 메모 (raw)   ← 메모에서 출발했으면 원문 보존
```

세부 절은 기능 성격에 맞게 가감하되, **5(스키마)·7(코드 가이드)·8(테스트)** 은 가능한 한 채운다.
→ 이 세 절이 `task-maker`가 작업을 잘게 쪼개는 근거가 된다.

## 작성 원칙

- **검증 가능하게:** "잘 되게 한다" 금지. "팔로워 0이면 하한 없음으로 처리" 처럼 판정 가능하게.
- **실제 모듈명 사용:** 추상적 표현 대신 `core/scraper.py:ScraperThread`, `data/selectors.csv` 등 코드와 1:1.
- **시그니처 수준 구현 가이드:** 함수명·인자·반환형까지 적어 task로 바로 분해되게.
- **솔직한 한계 명시:** (예: 봇 탐지 회피의 불완전성) 원본 메모의 현실적 단서를 Non-Goal/주의로 남긴다.
- **이미지 경로 명시:** 관련 스크린샷이 있으면 본문에 `.claude/tasks/파일.png` 경로와 용도를 적는다 (task-maker가 수집).

---

## 저장

- 파일명: `.claude/tasks/prd-YYMMDD[-N].md`
  - `YYMMDD` = 오늘 날짜 (예: 2026-06-10 → `260610`).
  - 같은 날 추가 PRD면 `-2`, `-3` … suffix (기존 파일 충돌 시 자동 증가).
- 메모 파일을 구체화한 경우, 그 파일을 **덮어쓸지 / 새 파일로 만들지** 사용자에게 확인.
  (기존 `prd-260610-3.md`는 메모→PRD 승격 시 같은 파일 덮어쓰기 + 부록에 원문 보존 방식을 씀.)
